# LightAudit

Explainable lighting-consistency auditing of edited images, with a relighting-attack evaluation.
Course project, Interactive Computer Graphics (semester 7).

In an outdoor photo one dominant light (the sun) lights every object. If an object or a damage region was pasted
in from a photo with different lighting, the light direction implied by its shading disagrees with the rest of
the scene. LightAudit estimates, for every region of a photo, which directions the light could come from, checks
whether one common direction explains all regions, shows the evidence in an interactive 3D viewer, says
"insufficient evidence" when it cannot tell, and then attacks itself (re-lights the fake to match the scene) to
measure how easily a forger could pass.

Verdicts: `CONSISTENT`, `SUSPICIOUS` (with the flagged regions), `INSUFFICIENT`, `CONFLICT`.
**A flag means "send for human review", never "this is fraud".**

## Quickstart (Windows 11, Python 3.11, no GPU)

```powershell
Set-ExecutionPolicy -Scope Process Bypass
.\setup.ps1                                   # venv + dependencies + backend check
.\run_all.ps1 -Quick                          # tests, synthetic data, calibration, demo bundles, quick evaluation
.\.venv\Scripts\python.exe -m lightaudit.cli serve
# open http://127.0.0.1:8000
```

The demo bundles in `bundles/` are already built, so the last two lines alone are enough to see the viewer.
Without FastAPI, `python -m http.server` from the project root and `http://localhost:8000/viewer/index.html`
also works (no upload, no live attack).

## What is in it

| Area | Where |
|---|---|
| Computer graphics | NumPy SDF ray-marcher for ground-truth scenes (`lightaudit/synth`); WebGL2 relighting shader (Lambert + Blinn-Phong / GGX), live residual heat map and counterfactual (`viewer/relight.js`); Three.js light dome with per-region probability landscapes, credible cones and a draggable light (`viewer/dome.js`); physics re-shade attack |
| Computer vision | Region proposals (SAM / SLIC / manual / ROI panel mode), surface-normal ensemble, per-region light estimation, glint and silhouette cues, consistency test with abstention |
| Image processing | Validity filtering, block bootstrap, isotonic fits, Reinhard colour transfer, JPEG / resize / noise robustness |
| ML | Pretrained SAM and normal estimators as black boxes, ensemble disagreement as uncertainty, gradient-boosted arbiter (ablation only), split-conformal alarm threshold |

Method in one paragraph: within a region, brightness is assumed to be an unknown *monotone* function of
`max(0, n·l)`. The light is the direction that maximises the rank correlation between the two (cue C1), which is
invariant to gamma, tone mapping, exposure and albedo scale. A spatial block bootstrap turns that into a
posterior map on an equirectangular direction grid; specular glints (C2), silhouettes (C3) and optional manual
shadow pairs (C4) refine it. Regions are fused by a weighted product; each region's leave-one-out *shortfall*
measures how badly it disagrees with the consensus of the others; the alarm level is a split-conformal quantile
of pristine calibration scenes. Details: [docs/METHOD.md](docs/METHOD.md).

## Useful commands

```powershell
$py = ".\.venv\Scripts\python.exe"
& $py -m lightaudit.cli setup-check                      # which optional backends work
& $py -m lightaudit.cli demo-bundles                     # rebuild the demo bundles
& $py -m lightaudit.cli audit-synth --sample normal:4000 --paste car:120 --name my_test --attacks
& $py -m lightaudit.cli calibrate --n-cal 200            # rewrites lightaudit/calib_default.json
& $py -m lightaudit.cli eval --suite quick               # experiments -> data/results
& $py -m lightaudit.cli figures                          # figures + tables
& $py -m pytest
```

## Auditing your own photo

Drop 10-20 outdoor photos of parked cars or street scenes (sunny, several objects visible) into `data/real/`.

```powershell
& $py -m lightaudit.cli audit --image data\real\photo.jpg --regions sam --normals dsine,stablenormal --html
& $py -m lightaudit.cli audit --image data\real\photo.jpg --roi dent_mask.png     # panel mode for a damage area
```

or use the "Upload a photo" card in the viewer gallery when it is served by `lightaudit.cli serve`.
Optional heavy models (`requirements-models.txt`) are downloaded on first use; if none works the pipeline falls
back to weaker estimators and says so in the bundle's backend log. If a normal estimator uses another axis
convention, `--flip-x/--flip-y/--flip-z` override the automatic check.

## Recalibrating on your own photos

The alert level only controls the false-alarm rate for photos like the ones used for calibration (synthetic
scenes by default). With a folder of your own *unedited* photos:

```powershell
& $py tools\calibrate_on_folder.py data\real_unedited --out calib_real.json
& $py -m lightaudit.cli audit --image photo.jpg --calib calib_real.json
```

## Limitations

> **What LightAudit can and cannot do.** LightAudit checks whether the lighting of different parts of a photo is physically consistent. It does **not** detect AI-generated images in general: a generator that produces the whole picture in one pass usually gives every object the same plausible light. A careful forger who re-lights an edited region to match the scene can pass the shading check (the attack lab measures exactly how much extra work that takes). Real photos can be flagged wrongly when they contain several lights, strong reflections, or bad surface-direction estimates, and many real photos (overcast, indoor, heavily filtered, tiny or flat objects) carry too little lighting evidence, in which case LightAudit says "insufficient evidence". Surface directions come from pretrained neural networks and are learned guesses, not measurements. The alert threshold controls the false-alarm rate only for photos like those used for calibration. **A flag means "send for human review", never "this is fraud".** Results on synthetic scenes do not automatically transfer to real photos; real-photo results are qualitative unless stated.

More: [docs/LIMITATIONS.md](docs/LIMITATIONS.md). What was actually run, the measured numbers and every deviation
from the build spec are in [BUILD_LOG.md](BUILD_LOG.md).
